Linux唤醒源记录节点

发表于2026-11-17|更新于2026-11-17|科普
|浏览量:

总述

Wakeup Source框架设计与实现 - Jayfan_Ma - 博客园

wakeup_sources 是 Linux 内核电源管理框架中用于记录、统计和管理所有“唤醒源（Wakeup Source）”状态与统计信息的调试节点。 它通常位于 /sys/kernel/debug/wakeup_sources 目录下，是排查系统无法休眠或异常唤醒的核心工具。

  • 硬件事件：例如电源按键中断、RTC 闹钟定时器、USB 插入检测、网络数据包到达（Wake-on-LAN）。
  • 软件事件：例如内核驱动或用户空间持有的唤醒锁（Wake Lock，常见于 Android 系统，通过 /sys/power/wake_lock 创建）。

wakeup_sources节点用处

在日常开发和功耗优化中，它主要有以下三大核心用途：

  • 排查“系统睡不下去”的元凶：当系统尝试进入休眠（如 echo mem > /sys/power/state）却失败，或者在息屏后依然耗电严重时，可以通过查看该节点找出是哪个模块一直处于活跃状态（持锁不放）。
  • 定位“系统被谁唤醒”的来源：如果设备在休眠期间频繁自动亮屏或唤醒，可以通过对比休眠前后的触发次数变化，精准定位触发中断的硬件驱动。
  • 评估系统功耗表现：通过统计各个模块的累计持锁时间（total_time）和最长单次持锁时间（max_time），开发者可以量化评估哪个驱动或服务最耗电。

怎么看懂它的内容

cat /sys/kernel/debug/wakeup_sources

字段名 含义说明 排查重点
name 唤醒源的名称(通常是驱动名、中断名或者锁名) 定位具体是哪个硬件或者软件模块
active_count 该唤醒源被激活的总次数 观察休眠前后该数值是否增加，可判断是谁唤醒了系统
event_count 触发唤醒事件的总次数 与active_count配合分析事件频率
wakeup_count 该唤醒源导致系统休眠中止(abort)的次数 数值持续增加，说明它一直在打断休眠流程
expire_count 超时自动释放的次数(针对设置了超时时间的锁) 判断是否存在超时机制的唤醒源
active_since 当前正处于激活状态的持续时间(毫秒) 最关键字段。只要该值大于0，说明它正在阻止系统进入休眠。
total_time 自系统启动以来，该唤醒源累计激活的总时间 数值越大，说明该模块让系统保持唤醒的时间越长，越耗电。
max_time 单次连续激活的最长时间 排查是否有驱动在某个时刻长时间卡住不释放锁。
last_change 最后一次状态发生变化(激活或者释放)的系统时间戳 结合内核日志时间，还原现场状态

典型实战排查逻辑

  • 场景 A：设备无法进入深度休眠
    执行 cat /sys/kernel/debug/wakeup_sources，重点筛选 active_since 不为 0 的行。如果发现某个驱动（例如 usb_otg 或某个自研驱动锁）的 active_since 一直在增长，说明它一直没有调用 pm_relax() 或释放锁，直接导致系统无法休眠。

  • 场景 B：设备休眠后瞬间自动唤醒
    记录休眠前的 wakeup_count 和 active_count。触发休眠并观察到异常唤醒后，再次查看该文件，对比哪一行的计数增加了，即可锁定触发唤醒的中断源。

    设备级关联节点：如果你已经锁定了某个具体外设，也可以直接访问 /sys/devices/<设备路径>/power/ 目录，里面同样包含该设备专属的 wakeup_count、wakeup_active_count、wakeup_total_time_ms 等独立属性文件。

event_count和active_count的区别：

  • event_count（事件总数）：只要驱动上报了一次唤醒事件（调用一次 pm_wakeup_event 或 pm_stay_awake），它就 +1。不管当前是不是已经处于激活状态。
  • active_count（激活次数）：只有当该唤醒源原本处于休眠/空闲状态（active == false），然后被重新激活变成活跃状态时，它才 +1。

在功耗排查中各自有什么用

  • 看 active_count（判断“打扰频率”）：
    它反映了这个模块独立发起工作周期的次数。如果 active_count 在短时间内飙升，说明硬件中断或定时器在频繁地一开一关（例如传感器每 100 毫秒唤醒一次系统，处理 5 毫秒后又睡下），导致系统无法进入深度休眠。
  • 看 event_count（判断“业务吞吐量”）：
    结合 active_count 一起看。如果 active_count 只有 5 次，但 event_count 高达 5000 次，说明每次唤醒后，该模块都在集中批量处理大量数据（例如网络下载或高速传感器采样），这是比较健康且省电的批处理模式。

如何在驱动代码中注册wakeup_source并使用pm_stay_awake()/pm_relax()防止系统休眠

方式一：基于 struct device 的标准接口（最推荐）

如果驱动已经关联了物理设备结构体（struct device *dev，如 platform、I2C、SPI 驱动），内核已经封装好了自动分配和释放生命周期的接口，无需手动管理 struct wakeup_source 指针。

  • 初始化：调用 device_init_wakeup(dev, true)，内核会自动为该设备创建并注册一个同名的 wakeup_source。
  • 阻止休眠（加锁）：在中断上下文或开始处理业务时调用 pm_stay_awake(dev)。
  • 允许休眠（解锁）：在工作队列或业务处理完成后调用 pm_relax(dev)。

方式二：手动注册独立的 struct wakeup_source

当你的驱动没有绑定具体的 struct device（例如纯内核线程、字符设备模块），或者同一个设备内部需要多个独立的唤醒源来分别统计不同子模块的耗电时，可以直接操作 wakeup_source 结构体。

  • 注册：wakeup_source_register(dev, "自定义名称")（传入 dev 可建立 sysfs 软链接，传入 NULL 则为纯软件源）。
  • 加锁与解锁：使用对应的 __pm_stay_awake(ws) 和 __pm_relax(ws)。
  • 注销：模块卸载时必须调用 wakeup_source_unregister(ws) 防止内存泄漏。

驱动开发中的 4 个避坑要点

  • 必须严格成对调用（否则导致永不休眠）：pm_stay_awake() 内部没有嵌套引用计数（这一点与 Regulator 不同）。连续调用 3 次 pm_stay_awake(dev)，只要调用 1 次 pm_relax(dev) 就会立刻解除激活状态；但如果调用了 pm_stay_awake() 后，在异常分支提前 return 而漏掉了 pm_relax()，系统将永远无法进入休眠（active_time_ms 会一直增长）。
  • 支持中断上下文：pm_stay_awake()、pm_relax() 以及带超时的 pm_wakeup_event() 内部均使用自旋锁（spinlock）保护，可以安全地在硬中断（IRQ Handler）或原子上下文中直接调用。
  • 超时保护机制（防死锁利器）：如果业务流程涉及与用户空间或外部芯片通信，担心对方无响应导致永远无法调用 pm_relax()，建议改用带超时的 pm_wakeup_dev_event(dev, msec, true)（或 __pm_wakeup_event(ws, msec)）。一旦超过 msec 毫秒，内核定时器会自动执行类似 pm_relax() 的释放操作。
  • 区分“阻止休眠”与“唤醒系统”：
    • pm_stay_awake() 的作用是系统当前醒着时，阻止它睡下去。
    • 如果系统已经处于深度休眠（Suspend to RAM），需要靠硬件引脚电平变化把 CPU 拉起来，必须在驱动中额外调用 enable_irq_wake(irq)（并在设备树节点中配置 wakeup-source; 属性），否则休眠期间硬件中断会被中断控制器屏蔽。
