异构架构

发表于2026-11-17|更新于2026-11-17|科普
|浏览量:

异构架构(Heterogeneous Architecture)：在同一颗芯片(SoC)或同一个系统内，集成两种或者以上不同指令集、不同微架构或不同功能定位的处理器核心。
旨在让不同特性的核心各司其职，从而同时兼顾高性能计算、实时控制与低功耗需求。

常见异构组合形式

  • 应用处理器+实时微控制器(MPU+MCU)：实际可以理解为SOC+MCU、SOC负责运行Linux/Android等复杂操作系统、处理图形界面与网络通信；MCU运行RTOS或者裸机程序，专门负责毫秒/微秒级的实时控制、传感器采集和低功耗待机

  • CPU + 专用加速器(NPU/DSP/GPU/FPGA)针对特定计算密集型任务进行硬件加速。CPU负责通用逻辑调度、NPU负责神经网络推理，DSP负责音视频编解码与信号处理，GPU负责图像渲染，FPGA负责灵活的硬件逻辑定制

  • 高性能大核 + 高能效小核(如ARM big.LITTLE)虽然指令集相同，但核心微架构与主频不同。重负载任务交由大核处理以保证速度，轻负载或后台任务交由小核运行以节省电量。

为什么嵌入式需要异构架构

  • 兼顾“丰富生态”与“硬实时性” 通用操作系统（如 Linux）虽然软件生态丰富，但中断响应延迟不可控，难以满足电机控制或工业总线的严格实时要求。将实时任务剥离给独立的 MCU 核心，可以从硬件层面彻底解决实时性瓶颈。
  • 极致优化能效比（PPA） 用通用 CPU 跑 AI 算法或信号处理不仅速度慢，而且发热量大。将数据交给专用的 NPU 或 DSP 处理，能以极低的功耗实现数倍甚至数十倍的算力提升。
  • 提升系统安全性与隔离度 不同核心可以运行在独立的权限域或安全域中。即使负责网络交互的 MPU 核心遭受攻击或系统崩溃，负责底层安全监控的 MCU 核心依然能够独立运作并执行安全保护。

开发中的核心技术挑战

  • 核间通信（IPC）与数据共享 不同核心之间需要高效交换数据，通常借助硬件邮箱（Mailbox）、共享内存（Shared Memory）以及 OpenAMP / RPMsg 等标准软件框架来实现。
  • 工具链与调试复杂度增加 开发者往往需要同时维护多套代码工程与编译器（例如 A 核用 GCC 编译 Linux 应用，M 核用 Keil/IAR 编译固件），且多核联合单步调试的难度远高于单核系统。
  • 资源分配与冲突管理 外设引脚、内存地址空间以及总线带宽需要在多个核心之间合理划分，防止出现资源抢占或数据竞争问题。

核间通信机制

在嵌入式异构系统（如 Cortex-A 运行 Linux + Cortex-M 运行 RTOS）中，核间通信（IPC）的核心思想是**“共享内存（Shared Memory）传输大数据 + 硬件中断（Mailbox/MU）触发通知”**，而 RPMsg（Remote Processor Messaging） 则是建立在这套硬件机制之上的标准化软件通信协议。

底层硬件基石：共享内存与硬件通知

不同架构的核心通常拥有独立的局部总线，但它们都会连接到同一片物理内存（如 DDR 或片上 SRAM）和核间中断控制器。

  • 共享内存（数据通道） 系统在物理内存中划出一块固定地址区域，同时映射到 A 核和 M 核的地址空间中。发送方直接将 payload 数据写入这块内存，接收方直接从同一物理地址读取，避免了传统总线（如 SPI/UART）的数据拷贝开销。
  • 硬件邮箱/消息单元（通知机制） 仅靠共享内存无法让接收方知道“数据何时写完”。芯片内部通常集成硬件单元（如 ARM MHU、NXP MU、TI Mailbox），当 A 核写完内存后，向该硬件寄存器写入一个值，即可立刻向 M 核触发一个硬件中断（IRQ），唤醒对方读取数据。

一次完整的 RPMsg 通信流程

假设 A 核（主核，运行 Linux）向 M 核（从核，运行 RTOS）发送一条控制指令，具体数据流转分为五步：

  1. 初始化与握手 A 核通过 Remoteproc 加载 M 核固件并启动它。M 核启动后，通过 RPMsg 的 Name Service（名称服务）向 A 核发送一条通告消息，声明自己创建了一个名为 "rpmsg-demo" 的通信端点（Endpoint，类似端口号）。
  2. 获取可用缓冲区 A 核应用层调用发送函数。RPMsg 层向底层的 Virtio Vring（在共享内存中维护的描述符表）申请一个空闲的 Buffer 块。
  3. 填充数据与更新指针 A 核在申请到的共享内存 Buffer 头部填入 RPMsg 包头（包含源地址、目的地址、数据长度），随后填入实际载荷数据，并更新 Vring 中“可用环（Avail Ring）”的索引指针。
  4. 触发硬件中断（Kick） A 核向硬件 Mailbox 写入特定标志，发出“Kick（踢一脚）”信号，M 核随即收到硬件中断并进入中断服务程序。
  5. 接收处理与回收内存 M 核响应中断，从 Vring 的可用环中取出 Buffer 地址并解析数据。处理完毕后，M 核将该 Buffer 放回“已用环（Used Ring）”并再次 Kick A 核，通知 A 核这块共享内存已释放，可以循环复用。

实际开发中的关键注意事项

  • Cache 一致性问题（最常见坑点） 现代处理器（尤其是 Cortex-A）带有数据缓存（D-Cache）。如果 A 核将数据写入了 Cache 却未刷新到物理内存，M 核去读共享内存时就会读到旧数据。解决方法通常是将共享内存区域在 MMU/MPU 中配置为 Non-cacheable（非缓存） 属性，或在收发前后手动执行 Cache Clean / Invalidate 操作。
  • 零拷贝（Zero-Copy）优化 标准的 rpmsg_send() 仍涉及一次从用户空间缓冲区到共享内存 Vring Buffer 的拷贝。在传输图像或高频传感器数据时，通常会使用 rpmsg_get_tx_payload_buffer() 直接获取共享内存指针，就地写入数据后再发送，实现真正的零拷贝。
  • 单包大小限制 默认情况下，单个 RPMsg Buffer 的大小通常为 512 字节（包含 16 字节包头，有效载荷为 496 字节）。如果需要传输几兆字节的大文件，通常不在 RPMsg 中直接切片，而是另辟一块大共享内存，仅用 RPMsg 传递“数据起始地址”和“长度”指针。
