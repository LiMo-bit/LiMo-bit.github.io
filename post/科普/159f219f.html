硬中断以及原子操作

发表于2026-11-17|更新于2026-11-17|科普
|浏览量:

总述

在 Linux 内核的**硬中断（IRQ Handler）或原子上下文（Atomic Context，如持自旋锁、软中断、禁用抢占期间）**中，代码执行遵循一条绝对铁律：绝对不能睡眠（休眠/阻塞/调度）。

这是因为硬中断借用的是被它打断的那个进程的内核栈，且中断处理期间调度器无法切换到其他任务。一旦调用了可能引发睡眠的函数，系统会直接触发 Kernel Panic（BUG: scheduling while atomic）。

详细说明

通用内核开发：硬中断中【可以调用】的操作

在硬中断中，只能执行非阻塞、无锁竞争或仅使用自旋锁、执行时间极短的操作：

  • 时间与极短延迟：
    • 获取时间：ktime_get()、jiffies 读取。
    • 忙等待微秒/纳秒级延时：udelay()、ndelay()、mdelay()（仅限极短硬件时序，通常不超过几十微秒，否则会拖垮系统实时性）。
  • 同步与锁机制：
    • 自旋锁（Spinlock）：spin_lock() / spin_unlock()（若该锁在进程上下文也会被获取，进程上下文必须用 spin_lock_irqsave() 防死锁）。
    • 原子变量与位操作：atomic_inc()、atomic_read()、set_bit()、test_bit()。
    • 完成量唤醒：complete() / complete_all()（仅唤醒等待者，本身不睡眠）。
  • 内存分配（严格限制标志位）：
    • 只能使用 GFP_ATOMIC 标志：kmalloc(size, GFP_ATOMIC)、kzalloc(size, GFP_ATOMIC)（从紧急内存池分配，内存不足时直接返回 NULL 而不会等待回收）。
  • 调度下半部（Bottom Half）：
    • 将耗时任务推迟执行：schedule_work()、queue_work()、tasklet_schedule()、irq_wake_thread()（触发线程化中断）。
  • 硬件 I/O 读写：
    • 内存映射寄存器读写：readl()、writel()、ioread32()、iowrite32()。

通用内核开发：硬中断中【绝对禁止】的操作

凡是底层可能触发 schedule()（进程调度） 或涉及用户空间访问的接口一律禁止：

  • 任何形式的睡眠函数：
    • msleep()、ssleep()、usleep_range()（它们会让出 CPU 挂起当前任务）。
  • 会阻塞的锁与同步原语：
    • 互斥锁（Mutex）：mutex_lock()（获取不到锁时会进入睡眠等待）。
    • 信号量（Semaphore）：down()（允许使用不阻塞的 down_trylock()，但禁止 down()）。
    • 等待完成量：wait_for_completion()、wait_event()。
  • 可能触发内存回收的分配：
    • 使用 GFP_KERNEL 标志的任何分配：kmalloc(..., GFP_KERNEL)、vmalloc()（vmalloc 内部必用 GFP_KERNEL）、devm_kzalloc(..., GFP_KERNEL)。
  • 访问用户空间内存：
    • copy_from_user()、copy_to_user()、get_user()、put_user()（若用户空间地址发生缺页异常 Page Fault，内核需要从磁盘换入页面，这会导致睡眠）。
  • 慢速总线通信接口：
    • i2c_transfer()、spi_sync()（I2C 和同步 SPI 传输需要等待总线时序完成，驱动内部几乎都使用互斥锁和 wait_for_completion 实现）。
    • 标准解决范式：传感器（如触摸屏、加速度计）通过 GPIO 触发硬中断后，在硬中断里只调用 pm_stay_awake() 并调度工作队列（或使用 request_threaded_irq 的线程函数），然后在工作队列/中断线程中再去执行 i2c_transfer() 读取传感器数据并操作 regulator_enable()。

如何快速判断一个内核函数能不能在中断里用？

如果你在看内核源码时不确定某个 API 是否安全，可以通过以下三个信号判断：

  1. 看函数注释：内核源码注释中若标注 Context: Process context. May sleep.（进程上下文，可能睡眠），则绝对不能在硬中断调用；若标注 Context: Any context.，则可以安全调用。
  2. 看函数参数：只要参数里包含 gfp_t flags，在中断中调用就必须传入 GFP_ATOMIC。
  3. 开启内核死锁/原子睡眠检测（开发阶段强烈建议）：在 menuconfig 中开启 CONFIG_DEBUG_ATOMIC_SLEEP=y。只要你在原子上下文不小心调用了会睡眠的函数，内核会立刻在 dmesg 打印出清晰的调用栈警告，帮你提前暴露隐患。
