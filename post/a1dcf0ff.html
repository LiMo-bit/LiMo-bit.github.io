IIC子系统

display

I2C子系统三层架构：I2C核心层(Core)、I2C总线驱动层(Adapter)和I2C设备驱动层(Clent/driver)

I2C 核心层（i2c-core.c）：提供注册/注销接口，以及通信方法的统一封装（如 i2c_transfer），屏蔽底层硬件差异。

I2C 总线驱动层（控制器驱动）：针对具体的 SoC I2C 控制器编写，负责产生起始信号、停止信号、读写时序。

  • struct i2c_adapter：代表一个物理 I2C 控制器（适配器）。
  • struct i2c_algorithm：包含实际的通信函数指针（核心是 master_xfer），挂载在 i2c_adapter 下。

I2C 设备驱动层（外设驱动）：针对挂在总线上的具体芯片（如 EEPROM、传感器）编写。

  • struct i2c_client：描述一个具体的 I2C 从设备（包含从设备地址 addr、所属的 adapter 等），通常由设备树（DTS）解析自动生成。
  • struct i2c_driver：设备的驱动程序，包含 probe()、remove() 和匹配表 id_table / of_match_table。

通信传输流程（面试高频）

  1. 设备树匹配：内核解析设备树节点生成 i2c_client，与注册的 i2c_driver 通过 compatible 属性匹配，触发 probe()。
  2. 构建消息：外设驱动在读写时，构建一个或多个 struct i2c_msg（指定从机地址、读写标志、数据缓冲区及长度）。
  3. 发起传输：调用核心层函数 i2c_transfer(client->adapter, msgs, num)。
  4. 底层执行：i2c_transfer 最终回调控制器驱动中 i2c_algorithm->master_xfer()，通过操作寄存器或 DMA 完成物理总线上的数据收发。

SPI 子系统

display

SPI 子系统的架构与 I2C 高度相似，同样分为：SPI 核心层、SPI 控制器驱动层（Master） 和 SPI 设备驱动层（Protocol Driver）。

核心架构与结构体

  • SPI 核心层（spi.c）：维护 spi_bus_type，提供驱动和设备的注册接口，以及数据传输的通用 API（如 spi_sync、spi_async）。
  • SPI 控制器驱动层：管理 SoC 内部的 SPI 控制器（产生时钟 SCLK、片选 CS 等）。
    • struct spi_master（新内核中逐步统一为 struct spi_controller）：代表一个 SPI 控制器，核心成员是 transfer_one_message（现代内核推荐）或 transfer。
  • SPI 设备驱动层：针对具体的 SPI 外设（如 Flash、LCD、网卡）。
    • struct spi_device：描述一个 SPI 从设备（包含片选号 chip_select、最大速率 max_speed_hz、工作模式 mode 如 CPOL/CPHA）。
    • struct spi_driver：外设驱动，包含 probe()、remove() 和匹配表。

通信传输流程（面试高频）

  1. 构建传输单元：外设驱动将要收发的数据封装进 struct spi_transfer（包含 tx_buf、rx_buf、len）。
  2. 打包消息：将一个或多个 spi_transfer 放入消息队列头 struct spi_message 中（使用 spi_message_init 和 spi_message_add_tail）。
  3. 发起传输：
    • 同步传输：调用 spi_sync(spi, &msg)（底层依赖完成量 completion，会阻塞当前进程直到传输完成，最常用）。
    • 异步传输：调用 spi_async(spi, &msg)（不阻塞，传输完成后触发回调函数 complete，可用于中断上下文）。
  4. 队列调度：控制器驱动的内核线程或工作队列（Message Queue 机制）依次取出 spi_message，拉低片选（CS），通过 FIFO/DMA 完成全双工收发，最后释放片选。

Linux 网络设备子系统

display

Linux 网络设备没有设备节点（/dev 下无文件），而是通过**套接字（Socket）**与网络协议栈交互。

  1. 核心架构（四层模型）
    • 网络协议接口层：统一协议栈与驱动的接口，核心函数为 dev_queue_xmit()（发送）和 netif_rx()（接收）。
    • 网络设备接口层：用 struct net_device 抽象所有网络设备，屏蔽底层硬件差异。
    • 设备驱动功能层：具体网卡的驱动实现，核心是填充 struct net_device_ops（如 ndo_open、ndo_start_xmit）。
    • 网络设备与媒介层：物理网卡芯片（MAC + PHY）。
  2. 两大核心结构体
    • struct net_device：代表一个网络接口（如 eth0、wlan0）。包含 MAC 地址、MTU、状态以及操作函数集 net_device_ops。
    • struct sk_buff（Socket Buffer）：网络子系统的“血液”。贯穿协议栈各层，通过移动内部指针（head、data、tail、end）来高效添加或剥离各层协议头（如 MAC 头、IP 头、TCP 头），避免内存拷贝。
  3. 数据收发流程（高频考点）
    • 发送流程：
      1. 应用层调用 write/send -> 协议栈封装成 sk_buff。
      2. 调用 dev_queue_xmit() -> 触发驱动注册的 ndo_start_xmit()。
      3. 驱动将数据映射到 DMA 缓冲区，通知网卡硬件发送，发送完成后触发中断释放 sk_buff。
    • 接收流程（NAPI 机制）：
      • 传统中断：每收一个包触发一次硬中断，高并发下会导致“中断风暴”。
      • NAPI（混合中断+轮询）：网卡收到首个包触发硬中断 -> 关闭网卡接收中断 -> 调度软中断（NET_RX_SOFTIRQ）执行驱动的 poll() 函数 -> 循环批量收包并调用 netif_receive_skb() 上送协议栈 -> 收完后再重新开启硬中断。

Linux WIFI子系统(802.11架构)

display

Wi-Fi 本质上也是一种网络设备（底层依然注册为 net_device），但由于涉及复杂的无线管理（扫描、认证、加密、漫游），Linux 引入了专门的 802.11 子系统。

  1. 整体分层架构（从用户态到硬件）
  • 用户空间配置工具：
    • wpa_supplicant（STA 客户端模式管理，负责连接、认证、WPA2/WPA3 握手）。
    • hostapd（AP 热点模式管理）。
    • iw（现代配置命令行工具，替代老旧的 iwconfig）。
  • 内核与用户态通信桥梁：nl80211：
    • 基于 Netlink 机制，负责在 wpa_supplicant 和内核 cfg80211 之间传递控制命令（如触发扫描、下发密钥）。
  • 内核配置管理层：cfg80211：
    • 所有 Wi-Fi 驱动的统一配置接口，管理无线设备状态（struct wiphy、struct wireless_dev），并向用户态暴露 nl80211 接口。
  • 内核协议实现层：mac80211（视芯片架构而定）：
    • 实现完整的 IEEE 802.11 MAC 层协议（帧封装、速率控制、聚合等）。
  • 硬件驱动与总线层：
    • Wi-Fi 模组通常通过 SDIO、PCIe 或 USB 接口与主控连接。

tty子系统

display

TTY 子系统是字符设备驱动的集大成者（如串口控制台、SSH 虚拟终端都基于它）

什么是TTY?

TTY（Teletypewriter，电传打字机）在 Linux 中是对终端设备的统称，本质上是一种特殊的字符设备。常见分类包括：

  1. 串口终端（/dev/ttyS*、/dev/ttyAMA*）：直接连接硬件 UART 控制器。
  2. 伪终端 PTY（/dev/pts/*）：成对出现（Master/Slave），用于 SSH 远程登录、桌面终端模拟器。
  3. 虚拟控制台（/dev/tty1 ~ /dev/tty63）：配合显示器与键盘使用。

TTY 核心三层架构（面试必背）

TTY 子系统采用经典的三层分层架构，核心目的是将“硬件通信”与“数据格式化处理”彻底解耦

TTY 核心层（TTY Core）

  • 职责：向上对用户空间提供统一的字符设备文件操作接口（file_operations，如 read、write、ioctl），向下管理各层对象的注册与生命周期。

  • 核心结构体：struct tty_struct（代表一个打开的终端实例）。

  • 线路规程层（Line Discipline，简称 N_TTY）

  • 职责（灵魂所在）：夹在核心层与驱动层之间的数据加工厂，负责处理输入/输出的特殊字符与交互逻辑。

  • 核心功能：

    • 回显（Echo）：你在键盘输入字符时，自动发回屏幕显示。
    • 行缓冲与编辑：支持退格键（Backspace）删除缓存中的字符，直到按下回车键（\n）才将整行数据交给上层应用。
    • 特殊字符转换与信号触发：如将 \r 转为 \n；识别 Ctrl+C 并转化为 SIGINT 信号发给前台进程。

  • 拓展：默认使用 N_TTY，但也可切换为其他规程（如蓝牙协议栈的 N_HCI、PPP 拨号的 N_PPP）。

  • TTY 驱动层（TTY Driver / UART 驱动）

  • 职责：直接与底层硬件打交道，只负责原始字节流的收发以及硬件参数配置（波特率、数据位、停止位、校验位），完全不关心数据内容。

  • 核心结构体：

    • struct tty_driver：描述一类 TTY 驱动，包含 struct tty_operations（如 open、write、set_termios）。
    • 嵌入式常用延伸（Serial Core 层）：为简化串口驱动编写，内核在 TTY 驱动层下又封装了 serial_core，驱动工程师只需实现 struct uart_driver 和 struct uart_ops（硬件收发寄存器操作）即可。

数据收发全流程（高频考点）

发送流程（应用层 write -> 硬件输出）

  1. 应用层调用 write() 写入数据，进入 TTY 核心层。
  2. 数据经过**线路规程（N_TTY）**处理（例如在规范模式下将 \n 转换为 \r\n）。
  3. 调用底层驱动的 tty_operations->write()（或 uart_ops->start_tx()）。
  4. 驱动将数据放入环形缓冲区（Ring Buffer），通过写硬件 FIFO 寄存器或 DMA 发送到物理引脚（TX）。

接收流程（硬件中断 -> 应用层 read）

  1. 物理引脚（RX）收到数据，触发 UART 接收硬中断。
  2. 中断服务程序（ISR）读取硬件 FIFO，将数据存入内核提供的 Flip Buffer（翻转缓冲区，tty_insert_flip_char），并调度工作队列（tty_flip_buffer_push）。
  3. 数据被推送至**线路规程（N_TTY）**进行加工（处理回显、识别 Ctrl+C、缓存整行数据）。
  4. 唤醒正在阻塞等待 read() 的应用层进程，将数据拷贝到用户空间。
  • tty 与 console（控制台）的区别？
    • TTY 是交互式字符设备，供用户态进程读写。
    • Console 是内核态输出调试信息（printk）的通道，通常是只写的。在嵌入式系统中，控制台往往绑定在某个具体的串口 TTY 设备上（通过内核启动参数 console=ttyS0,115200 指定）。
  • 为什么要有 Flip Buffer（翻转缓冲区）？
    • 接收数据发生在硬件中断上下文（要求执行极快且不能睡眠），而线路规程处理数据可能耗时较长。使用双缓冲区交替翻转，中断里只管往里塞数据，随后交给下半部（工作队列）慢慢向线路规程推送，避免丢包并防止中断阻塞。

Input 输入子系统

display

Input 子系统专门用于管理按键、触摸屏、鼠标、键盘、加速度传感器等输入设备。它的核心思想是将“硬件事件采集”与“用户态事件分发”彻底解耦。

  1. 核心三层架构
  • 设备驱动层（Input Driver）：直接操作硬件（如 GPIO 按键中断、I2C 触摸屏），只负责读取物理状态并上报原始事件。
    • 核心结构体：struct input_dev（描述一个输入设备，通过 set_bit() 声明支持的事件类型）。
  • 输入核心层（Input Core，input.c）：承上启下的中枢，维护 input_dev 链表和 input_handler 链表，并自动完成两者的匹配（input_attach_handler）。
  • 事件处理层（Event Handler）：与用户空间交互，创建 /dev/input/eventX 设备节点，实现 file_operations。最常用的是通用事件处理器 evdev.c（还有 mousedev、joydev）。
  • 事件上报全流程（面试高频）
  1. 初始化与注册：驱动分配 input_dev（input_allocate_device），设置支持的事件类型（如 EV_KEY 按键、EV_ABS 绝对坐标、EV_REL 相对坐标），调用 input_register_device() 注册。
  2. 触发与采集：用户按下按键或触摸屏幕，触发硬件中断（通常在中断下半部或线程化中断中读取 I2C 坐标）。
  3. 事件上报：驱动调用 input_report_key() / input_report_abs() 上报数据，最后必须调用 input_sync()（发送 EV_SYN 同步事件，标志一帧完整数据上报结束）。
  4. 用户态读取：核心层将事件分发给匹配的 evdev，存入环形缓冲区并唤醒阻塞的进程。应用层通过 read() 读出标准结构体 struct input_event（包含时间戳 time、事件类型 type、事件码 code、值 value）。

显示子系统：Framebuffer vs DRM

display

在现代 Linux 面试中，面试官不仅会问传统显示，更看重你是否了解 DRM 如何替代 Framebuffer。

  1. 传统 Framebuffer（帧缓冲，/dev/fb0）
  • 核心原理：将显存（物理内存）抽象为一个连续的线性字节数组，驱动将显存通过 mmap() 直接映射到用户空间，应用层往这块内存写像素数据（RGB），硬件 LCD 控制器（DMA）自动将其扫描到屏幕上。
  • 核心结构体：struct fb_info（包含可变参数 var 如分辨率/色深、固定参数 fix 如显存物理地址、操作集 fb_ops）。
  • 致命缺陷（被淘汰原因）：
    • 不支持多图层硬件合成（只能靠 CPU 软件混合，性能差）。
    • 不支持 GPU 硬件加速与显存共享（零拷贝）。
    • 缺乏完善的垂直同步（VSync）机制，容易出现画面撕裂。
  • 现代 DRM 子系统（Direct Rendering Manager，/dev/dri/card0）

DRM 是现代 Linux（Android、Wayland、桌面及高端嵌入式）的绝对主流，统一管理显示输出与 GPU 渲染。

  • 核心两大模块：
    1. KMS（Kernel Mode Setting，内核模式设置）：负责显示输出控制（设置分辨率、刷新率、控制显示管线、多图层合成与 Page Flip 翻页）。
    2. GEM（Graphics Execution Manager，图形执行管理器）：负责显存分配与生命周期管理，配合 DMA-BUF 实现 CPU、GPU、VPU（编解码）之间的零拷贝内存共享。
  • KMS 显示管线核心组件（面试必背流水线）：
    数据流向遵循严格的硬件流水线顺序：FB → Plane → CRTC → Encoder → Connector
    • Framebuffer（FB）：存放像素数据的内存缓冲区（对应 DRM 里的 drm_framebuffer）。
    • Plane（图层）：硬件叠加层（如 Primary 主图层、Overlay 视频叠加层、Cursor 光标层），负责将多个 FB 的图像混合裁剪。
    • CRTC（显示控制器）：显示管线的核心大脑，负责生成时序（Timing）、控制扫描输出、触发 VSync 中断。
    • Encoder（编码器）：将 CRTC 输出的并行像素流转换为特定协议信号（如 MIPI-DSI、LVDS、TMDS）。
    • Connector（连接器）：代表物理输出接口（如 HDMI、eDP、MIPI 屏幕），负责检测热插拔（HPD）和读取屏幕参数（EDID）。

面试总结：Framebuffer 与 DRM 核心对比

对比维度 Framebuffer（FB） DRM（KMS + GEM）
设备节点 /dev/fbX /dev/dri/cardX、/dev/dri/renderDX
多图层合成 不支持（需 CPU 软件合成） 支持硬件 Plane 叠加，大幅降低 CPU 负载
防止画面撕裂 需手动通过双缓冲 + FBIOPAN_DISPLAY 实现 原生支持 Atomic（原子提交） 与 VSync 异步翻页（Page Flip）
内存与零拷贝 单一连续物理显存，难与 GPU 共享 GEM + DMA-BUF，支持多硬件模块零拷贝共享
多屏显示 架构僵硬，难以动态管理 原生支持多 CRTC / Connector 动态路由与热插拔

V4L2 核心四层架构与结构体（面试必背）

display

在 Linux 驱动与多媒体岗位面试中，**V4L2（Video4Linux2）**是复杂度最高、含金量也最高的子系统之一。现代嵌入式 Camera 链路通常由 Sensor（传感器） → MIPI CSI-2 接收器 → ISP（图像信号处理器） → DMA 写入内存 组成。

内核中为什么禁止在持有 spinlock 时调用 copy_from_user 或 msleep

display

持有 spinlock（自旋锁）期间处于原子上下文（禁止睡眠与调度），而 copy_from_user 和 msleep 都会引起进程睡眠，一旦发生调度极易导致系统死锁或内核崩溃（Kernel Panic）。
